# Spec: Background Agent sounds and independent desktop notifications

## Problem Statement

用户会在 ctty7 中同时运行多个编程 Agent，并在它们工作时切换到其他应用。现有的 done、run、idle、input 标记能够在 ctty7 可见时说明各个窗格的状态，但当 ctty7 在后台时，用户无法通过声音得知某一轮已经结束，或某个 Agent 正在等待输入。

ctty7 已有桌面通知和终端 BEL 设置，但没有专门的 Agent 通知音效。现有会话内桌面通知还要求 Agent 通过 hooks 上报完整状态，而界面显示的 Agent 状态可以结合 hooks 与屏幕识别。如果只在现有的 hooks 通知分支中加入声音，已经支持屏幕状态识别的 Agent 仍然无法获得这项体验。

## Solution

为所有受支持且能够判断状态的 Agent 提供统一的提醒行为。Agent 实时进入 done 或 input 状态时，根据用户独立设置的两个通知渠道，播放短提示音、发送桌面通知、同时执行两者，或保持安静。

使用用户指定的 Codex App Default 通知音频。声音提示用户返回 ctty7，现有状态标记则帮助用户找到已经完成或需要输入的窗格。播放提示音不能把结果标记为已读。

两个渠道各自提供“关闭”“仅整个 App 未聚焦时”“总是”三个选项。新安装默认两项均为“仅整个 App 未聚焦时”。升级时保留用户原有的桌面通知偏好，并将新增的 Agent 提示音设置初始化为“仅整个 App 未聚焦时”。只要任意 ctty7 窗口获得焦点，整个 App 就属于前台，包括与事件来源不同的窗口、标签页或窗格。

桌面通知与提示音独立控制。用户可以只开声音、只开桌面通知、两者都开，或两者都关。Windows、macOS、Linux 均提供内置音频播放、声音策略和试听控件，使用相同的 Agent 事件与焦点规则。

## User Stories

1. 作为正在使用其他应用的用户，我希望 Agent 完成一轮时能听到提示音，以便回来查看结果。
2. 作为正在使用其他应用的用户，我希望 Agent 需要输入或授权时能听到提示音，以免它长时间等待而我没有察觉。
3. 作为使用 Codex、Claude、Cursor 或其他受支持 Agent 的用户，我希望它们遵循统一的通知规则，以便这项能力不受 Agent 品牌限制。
4. 作为使用屏幕识别来判断 Agent 状态的用户，我希望识别到的 done 和 input 状态变化也能触发提醒，以便通知不局限于已安装完整状态 hooks 的 Agent。
5. 作为正在查看 ctty7 的用户，我希望默认保持安静，以便通过现有状态标记跟踪任务而不受额外打扰。
6. 作为打开多个 ctty7 窗口的用户，我希望任意窗口聚焦时都抑制整个 App 的后台提醒，以便“后台”指的是整个应用。
7. 作为选择“总是”的用户，我希望 ctty7 在前台时也能提醒，以便自行覆盖默认的前台静音行为。
8. 作为选择“关闭”的用户，我希望对应渠道停止提醒，以便控制受到的打扰。
9. 作为偏好只听声音的用户，我希望关闭桌面通知后仍能保留提示音，以便无需显示横幅。
10. 作为偏好视觉提醒的用户，我希望只收到桌面通知而没有声音，以便保持安静。
11. 作为需要两个渠道的用户，我希望桌面通知出现时播放一次短音，以便同时获得两种反馈。
12. 作为为两个渠道选择不同策略的用户，我希望桌面通知和声音分别判断是否提醒，以便其中一项可以设为“总是”，另一项设为“仅后台”或“关闭”。
13. 作为关闭了 Windows 通知横幅的用户，我希望已开启的 Agent 提示音仍然可用，以便视觉渠道不控制音频播放。
14. 作为收到声音提醒的用户，我希望使用熟悉的 Codex Default 音效，以便听到所指定的声音。
15. 作为配置功能的用户，我希望能试听音效，以便无需等待任务完成或把 App 切到后台。
16. 作为听到完成提示后返回的用户，我希望未读结果的 done 标记继续保留，以便找到完成的任务。
17. 作为听到输入提示后返回的用户，我希望 Agent 仍在等待时保留 input 标记，以便找到需要处理的操作。
18. 作为查看结果的用户，我希望继续使用现有的 done 已读后转为 idle 的行为，以便通知投递不改变状态语义。
19. 作为 Agent 持续等待输入的用户，我希望同一次等待只提醒一次，以免重复轮询不断响铃。
20. 作为 Agent 恢复运行后再次需要输入的用户，我希望收到新的提醒，以便区分不同的等待过程。
21. 作为多个 Agent 同时完成任务的用户，我希望声音不重叠，也不积压播放队列，以便一批事件只产生简短提醒。
22. 作为重启或重新连接 ctty7 的用户，我希望旧的 done 和 input 状态只用于建立初始状态而不再次响铃，以免历史状态被误认为新的任务事件。
23. 作为启动 Agent 后看到空闲输入框的用户，我希望不收到完成提醒，以免启动会话被误认为完成任务。
24. 作为 Agent 状态未知的用户，我希望不产生推测的完成或输入提醒，以免静默或无法识别的画面被当作成功。
25. 作为在已连接的远程机器上运行 Agent 的用户，我希望观测到的事件通过本地桌面 App 播放提示音，以便在当前使用的电脑上听到提醒。
26. 作为已有用户，我希望升级时保留桌面通知偏好，以免启用新功能覆盖原来的选择。
27. 作为关闭了专用提示音的用户，我希望 Agent 桌面通知也保持静音，以便声音设置同时避免这些通知播放 Windows 默认通知音。
28. 作为没有安装 Codex App 的 ctty7 用户，我希望音频随 ctty7 打包，以便播放不依赖其他应用或网络下载。

## Implementation Decisions

- 使用现有 Agent 领域状态：Working 显示为 run，Waiting 显示为 input，Done 显示为 done，Idle 显示为 idle。Unknown 保持未知。“完成”表示观测到一轮结束；短提示音不代表用户的整体目标已经成功实现。
- 实时通知事件必须来自与可见状态标记相同的、合并后的 Agent 状态。不能读取界面标签文字，也不能把通知资格限定为完整状态 hooks。保留现有 hooks 与屏幕识别的优先级和状态稳定规则。
- 已知正在进行的一轮实时进入 Done 时，产生完成事件；实时进入 Waiting 时，产生输入事件。初始快照、启动时的 Idle、Unknown、恢复连接和重建窗格用于建立初始状态，不作为新事件。
- 优先使用现有生命周期信息，按窗格、会话和实时事件过程去重。重复观测到 Done 或 Waiting 时保持安静。Unknown 或短暂缺失的状态报告不能重新触发同一次等待提醒；确认恢复到 Working 后，可以允许下一次等待提醒。前台被抑制的事件视为已经处理，不能在 App 后续失去焦点时补发。
- 新增 Agent 提示音策略，提供“关闭”“仅整个 App 未聚焦时”“总是”。复用项目现有的通知策略词汇、序列化约定、配置持久化和设置实时生效机制。
- 保留现有桌面通知策略及其存储值。在设置说明中明确它也控制 Agent 的 done 和 input 提醒。新增声音策略独立生效，适用于 Agent 提醒，不适用于普通命令完成通知。
- 将 Agent 提示音策略与“试听”操作放在通知设置附近。第一版的 done 和 input 共用指定的 Default 音效；分别控制两个事件的开关和音效选择不属于本次范围。
- 在整个 App 范围内判断焦点。只有没有任何 ctty7 窗口获得焦点时，才允许“仅后台”渠道投递。事件来源窗口在后台、但另一个 ctty7 窗口聚焦时，不能响铃。异步播放开始前重新检查对应策略和焦点。
- 同一个实时事件分别评估声音与桌面通知。任意渠道设为“关闭”都不能阻止另一个渠道的判断。某一渠道投递失败或权限被拒绝，不能阻止另一渠道。
- Windows 上的这类 Agent 桌面通知必须静音投递。音频由 App 主动播放，保证只开声音或两个渠道都开时，不额外响起 Windows 默认通知音。保留点击跳回来源窗格和现有通知上下文信息。
- 打包用户指定的 Codex App Default WAV 原始音频。已检查素材大小为 109,686 字节，时长约 0.571 秒，双声道，采样率 48 kHz。SHA-256 为 d3ec08b617dedc0d46de8da082e83fcd7526e129bbf6ce14354ee7f182a4e2ba，用于标识指定素材；将音频导入仓库属于后续实现工作。
- 异步播放音频，不阻塞界面渲染或 Agent 状态处理。优先使用平台原生音频能力和已有依赖。短音播放不应要求启动 PowerShell 子进程、安装 Codex App 或引入新的通用音频框架。
- 同一时刻最多播放一个 Agent 提示音。播放期间到来的密集事件可以共用正在播放的提醒，不排队延迟播放。保留每个窗格的状态和独立开启的桌面通知。
- 试听使用同一份打包音频和播放路径，绕过常规事件及焦点策略。试听不能伪造 Agent 事件、发送桌面通知，或把结果标记为已读。
- 终端 BEL 行为继续由独立设置控制。终端响铃不能成为新 Agent 提示音的触发源，fork 现有的 BEL 默认关闭行为继续适用。
- 不改变状态检测以及 CLI、daemon 协议中的词汇。远程观测到的 Agent 事件使用本地 App 的偏好和扬声器。桌面 App 已关闭时，不承诺提供提醒服务。
- 三个平台使用本地原生音频能力。Windows 使用 PlaySoundW，macOS 使用 NSSound，Linux 使用 PulseAudio simple API，也适用于提供 PulseAudio 兼容服务的 PipeWire 桌面。音频素材始终内置，不依赖外部播放器；Linux 源码构建与发行构建包含客户端开发库，桌面音频服务由用户的操作系统提供。
- 无音频设备、音频服务不可用或播放失败时记录错误并释放播放占用，后续事件仍可再次尝试。声音失败不能影响桌面通知或 Agent 状态。

## Testing Decisions

- 用户已经确认行为验收：后台完成响一次、默认前台完成不响、受支持 Agent 共用规则、返回后保留 done 标记、恢复旧会话不补响、同时完成不叠音。input 提醒也采用相同的事件和焦点检查。
- 优先使用一个已有的应用与视图集成测试入口：输入 Agent 生命周期状态和 App 焦点，通过能够记录投递请求的适配器观察桌面通知与音频播放请求。验证用户可见行为，不测试私有辅助函数调用或样式、配置常量。
- 参考现有真实视图中的 Agent 状态、聚焦与未聚焦时的未读结果、会话重建和屏幕状态回归测试。通过通知入口覆盖 hooks 与屏幕识别合并后的状态，包括没有完整 hooks 的屏幕识别 Agent，以及 hooks 观测到的短回合。
- 在 App 聚焦和未聚焦两种情况下，分别验证两个渠道的策略。覆盖只开声音、只开桌面通知、两者都开、两者都关，以及“总是”与“仅后台”混合配置。覆盖事件来源窗口未聚焦、第二个 ctty7 窗口聚焦的情况。
- 覆盖实时 Working 转 Done、Working 转 Waiting、重复状态报告、Waiting 转 Working 后再次转 Waiting、Unknown 间隔、初始 Idle／Done／Waiting 快照、重连和重建窗格。验证每次事件只提醒一次，且被抑制后不会因焦点变化而补发。
- 验证声音投递不会清除未读完成状态。返回无关窗格不能把结果标记为已读；查看对应结果继续使用现有已读行为。
- 验证多个事件争用播放时的行为、音频密集事件期间桌面通知独立投递，以及 App 在前台或自动声音设为“关闭”时仍可试听。试听不能改变 Agent 状态或未读标记。
- 验证源音频身份与发行包内容，确保安装后的应用无需 Codex App 或网络即可播放。在 Windows 通知投递入口验证 Agent 弹窗为静音。
- 在 Windows 原生应用中验收真实可听播放、前后台焦点、第二个窗口、关闭系统横幅后只开声音、点击通知跳转、试听及无双重响铃。记录到音频请求不能代替实际播放成功的证据。
- Windows、macOS、Linux CI 均执行生命周期、独立渠道、多窗口焦点、投递前复查、声音争用、设置持久化和试听点击测试。原生播放代码必须在各平台生产构建中编译，Linux 发行构建也必须具备所需音频客户端库。
- 如实区分代码和策略测试通过、原生播放路径已编译以及实际设备播放验收。CI 和记录适配器不能代替扬声器输出证据；无法现场运行的平台在 PR 中注明未验证实际听感。

## Out of Scope

本次不包括朗读任务名称或文字转语音、Classic 或自定义音效选择、多套声音主题、按 Agent 分别设置、按窗格判断焦点、done 与 input 的独立事件开关、重复催办提醒、普通命令完成提示音、终端 BEL 重设计、侧栏或 Header 重设计、新增 Agent 检测规则或为不受支持 Agent 推测状态、桌面 App 退出后后台播放，以及在编写规格阶段发布软件版本。

## Further Notes

用户明确选择了 done 和 input 都提醒、按整个 App 判断焦点，以及上述行为验收。同时要求桌面通知和声音各自独立控制，由 ctty7 提供默认值，保留用户选择权。

截至 2026-10-11 检查时，上游 tty7 main 已有终端 BEL 声音和桌面通知，但没有专用的、统一由 Agent 状态驱动且可独立设置策略的通知提示音。本规格描述的是相对于当前已检查上游的功能差异，不表示上游完全没有声音能力。相关上游工作包括 l0ng-ai/tty7#359 和 l0ng-ai/tty7#1062；现有状态标签行为由 cloudy-liu/ctty7#100 及后续改进记录。

按照项目的 Issue Tracker 约定，使用 cloudy-liu/ctty7 的 GitHub Issues，并添加 ready-for-agent 标签。规格已具备进入实现规划的条件；发布规格不代表功能已经实现。
